# P5.1 Milestone 4 — product wiring implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the Arca engine reachable by a user — `gascand` selected onto it, starting it itself from a bumped pin, with its artifacts fetched and verified, its facts in `gascan doctor`, and `offline` earned rather than asserted.

**Architecture:** Four landings in a hard dependency chain. Arca and the frozen `containerization` submodule are fixed first and sealed with one signed tag; the pin bumps and the artifacts publish against that tag; Gas Can is then wired against a *real pinned engine* rather than a local build; and the offline proof runs last, setting a certified-revision constant in Gas Can that gates `Capabilities.offline` client-side. The chain is not a preference — `crates/gascan-engine-proto/build.rs:27` generates the Rust client from the pinned revision, so field 20 is invisible to Gas Can until the pin moves.

**Tech Stack:** Swift 6 / SwiftPM (Arca, `containerization` submodule), Rust (Gas Can workspace), protobuf + grpc-swift + tonic, `pkgbuild`/Homebrew cask packaging, bash release scripts.

**Design:** `docs/superpowers/specs/2026-08-16-p5-1-milestone-4-product-wiring-design.md`

## A NOTE ON THIS PLAN'S SHAPE — READ IT BEFORE TASK 1

**Landing 1's Tasks 1 and 2 are expanded to the step. Everything after them carries files, interfaces, tests and acceptance criteria but not step-by-step code, and that is deliberate.**

This project has measured the cost of guessing ahead. Milestone 2's plan guessed at Swift and shell it had not built against and **nine blocks were wrong**, every one surfacing as a correction and the worst of them silent. Milestone 3's plan records the same result at task granularity: "Task 1's brief carried full Swift and three of its details were wrong — a test fixture that did not exist, `VolumeManager` typed as a plain object when it is an `actor`, and six anchors that were five. Tasks 2 and 3 received requirement-level briefs and produced stronger work, because the implementer re-derived from the code rather than transcribing the controller's guesses."

Tasks 1 and 2 are expanded because their current source was read in full while this plan was written. Everything else is expanded to requirements.

**Expand each landing after the preceding one lands. Do not expand from reading alone.**

### The mutation rule, because it is what milestone 3's worst defect evaded

Milestone 3's resize test **shipped the control instead of the subject**. The commit that introduced it recorded the variant *with* a readiness handshake passing against the broken engine — and that is the variant that was committed, under a name describing the window the handshake closes. Reverting the engine fix would have left both repositories green.

So for every fix in this plan:

1. Write the test. Run it against the **unfixed** code and **see it fail**, with the failure output recorded.
2. Apply the fix. See it pass.
3. **Mutate the fix in two different ways and confirm the two mutations fail disjoint sets of tests.** That is what proves no test is riding on another's fix.
4. A test whose name describes a window must not close that window before testing it.

- [ ] **Step 3: Make the refusal explicit**

**CORRECTED 2026-08-16 by Task 2's implementer — this step first said to derive the range from "the platform, `1...SIGRTMAX` where available, otherwise `1..<NSIG`", and that instruction was wrong twice over.** Arca runs on macOS, where `SIGRTMAX` does not exist, so the rule always lands on `NSIG` — which is 32 on Darwin, giving `1...31`. But the number `parseSignal` returns is handed to a **Linux guest**, and the two do not share a numbering (Darwin's `SIGUSR1` is 30, Linux's is 10; Darwin's `SIGSTOP` is 17, Linux's is 19). Bounding a Linux signal by the host's signal count validates against a space the value does not live in, and it refuses 34-64 — the Linux real-time signals the guest genuinely accepts and that `docker kill --signal 34` legitimately asks for.

**Derive the range from `Containerization.Signal.linux`**, the dependency's own table: `Set(Containerization.Signal.linux.values)` yields `1...31` ∪ `34...64`, correctly excluding the 32/33 RTMIN gap. That is not a copied literal, which is what "do not copy a bound from here" was guarding against. **It is also already this repository's answer to the same question** — `ExecManager.signalExec` validates against the same map (`ExecManager.swift:442`: "the right map because `LinuxProcess.kill` sends…"), and `ExecSignalTests` documents 32 and 33 as its test values because they are the two numbers a range written as `1...64` would wrongly admit. The brief's rule would have left the container-kill and exec paths disagreeing.

Both branches refuse rather than default, and the error names the offending input — the original string the caller typed, not the `SIG`-stripped form, because that is what the 400 quotes back.

**`package` alone is not enough: use `nonisolated package func`.** `ContainerManager` is a `public actor` (`ContainerManager.swift:14`), so a merely-`package` method is actor-isolated and reachable only as `try await`, while `XCTAssertThrowsError` takes a non-async `@autoclosure`. The file already uses `nonisolated` deliberately for `logManager`, `imageStoreRoot` and `layerCachePath`.

**One table for names and numbers widens the accepted names beyond the original thirteen** — `parseSignal("ABRT")` returns 6 rather than being refused. **RULED 2026-08-16: keep the widening.** Validating numbers against the Linux table while refusing names outside a hand-written thirteen would accept `--signal 6` and refuse `--signal ABRT` for the same signal. It also matches Docker, which accepts the full table. This is a deliberate behaviour change on Arca's Docker surface, covered by a test that — unlike the thirteen-name guard — does fail against the unfixed code.

## Task 3: The startup SIGTERM race — defect 4, exit 143

**Files:**
- Modify: `Sources/arca-engine/ArcaEngineCommand.swift` — the window closes at `signal(number, SIG_IGN)` (`:430` as re-derived 2026-08-16) and `source.resume()` is at `:503`
- Test: `Tests/ArcaEngineTests/EngineStartupTests.swift`, and the live arm in `crates/gascan-arca/tests/live/shutdown.rs:304`

**Requirements, not steps.**

The window is **the whole of startup**, not bind-to-`SIG_IGN`: SIGTERM's disposition is default from `exec`, so argument validation, the vminit load and all three `initialize()` calls — including the one constructing a real `VmnetNetwork` — are inside it. Bind-to-`SIG_IGN` is merely the part a *client* can observe, because no socket exists before bind.

**143 is always the kernel and never the engine.** `128+15`, and the engine's only deliberate exit is `Foundation.exit(status)` at `ArcaEngineCommand.swift:336` — one call site, verified. Do not accept a fix that merely converts 143 into a different code.

**The fix is a design change, not a one-liner.** The handler closures capture the engine, and a bare `SIG_IGN` installed before a resumed dispatch source would turn a startup SIGTERM into a **silent no-op**, which is worse than dying — a user's `launchctl`-free `kill` would appear to do nothing. Whatever is built must make a startup SIGTERM *act*, not vanish.

**Measure the second window, which has never been measured by anyone.** Between `signal(number, SIG_IGN)` and `source.resume()` the disposition is already `SIG_IGN` but libdispatch has not registered the kevent, so a signal there is lost outright and the live tier would report `"the engine ignored SIGTERM"` — reading as a shutdown defect rather than a startup one. Measure it before and after the fix. Report the numbers whichever way they come out.

**Acceptance:** the forced instrument is re-run and reports **0/12 on the arm that signals inside the engine's own startup** — after its state database exists and before its socket does — with the arms interleaved in one process against one binary. A naturally-occurring rate (~2 in 440) is not an acceptance criterion; it cannot distinguish a fix from luck at that sample size.

**CORRECTED 2026-08-16 by Task 3's implementer, who measured the criterion this plan first wrote and showed it unachievable.** It originally demanded 0/12 on the **immediately-after-spawn** arm. That arm signals into `dyld`, not into the engine: instrumenting the load with `clock_gettime(CLOCK_MONOTONIC)` across 8 spawns of a warm binary linking 40 libraries measured **10-13ms between `posix_spawn` returning and the engine's first instruction** (one cold-inode outlier at 732ms). `posix_spawn` returns as soon as the child exists, so a parent signalling immediately signals into that interval every time. **No code inside the process can run there and no disposition it sets can apply**, so that arm reads 12/12 before and after the fix, and always will.

**The only thing that closes the loader window is the launcher**, and only half of it is Arca's. A signal blocked between `fork` and `exec` is *pending* rather than fatal and survives the loader; the engine's `arca_signal_capture_install` ends with `sigprocmask(SIG_UNBLOCK, …)`, so a pending signal is delivered the instant the handler exists. That unblock is independently a correctness fix — an engine spawned with SIGTERM already blocked would otherwise install a perfect handler and be unkillable. **The launcher's half is not implemented and is a decision for Task 11:** `common::SUPERVISOR` is a `/bin/sh` wrapper and a shell cannot set a signal mask, while doing it in Rust needs `Command::pre_exec`, which the Gas Can workspace's `unsafe_code = "forbid"` rules out.

The implementer did not change the instrument to make the number move, which would have made the criterion pass by changing the measurement.

## Task 11: The engine supervisor — dial first, spawn on miss

**Files:**
- Create: an engine supervisor module under `crates/gascand/src/`
- Reuse: `crates/gascan/src/daemon.rs:451` (`DaemonSpawner`), `crates/gascan/src/client.rs:327` (`TokioDaemonSpawner`)
- Reuse: `crates/gascand/src/socket.rs:631` (`validate_peer_uid`), `PeerUid`

**Requirements, not steps.**

**This supersedes parent design §2.3's launchd job**, on the reasoning in design §2.1. Dial the engine socket first; spawn only when nothing answers. §2.3's own conclusion — that recovery *requires* dialing an existing engine — makes dial-first the primary path and spawn its miss arm.

**Validate the engine socket's owning uid before dialing.** Nothing does this today: `validate_peer_uid` is used at `crates/gascand/src/api.rs:485-491` for the opposite direction, the daemon checking clients of *its own* socket. This is new code; `PeerUid` is the piece to reuse.

**An engine that dies mid-call fails that call** and appears as `MissingOwned` on the next reconcile — never a silent reconnect implying state survived. `run_daemon` already calls `service.reconcile()` before serving (`crates/gascand/src/main.rs:483`), and `ReconcileFinding` (`crates/gascand/src/reconcile.rs:5-21`) already carries `MissingOwned`.

**A surviving engine is a feature, not a leak.** A restarted daemon adopts running sandboxes by owner labels. Do not add code that kills an engine it did not start.

**Do not import `applyRestartPolicies()`-shaped behaviour.** An engine that resurrects sandboxes before its socket binds is one the consumer never sees transition.

**Acceptance:** with an engine already listening, no second engine is spawned; with none, exactly one is; with a socket owned by another uid, the dial is refused before connecting. Each proved by a test that fails without the corresponding branch.

- Read: `engine/arca-pin.json` schema 2 from Task 9

**Requirements, not steps.**

**Not in `install.sh`.** `packaging/macos/render-cask.sh` emits `pkg "gascan-#{version}-macos-arm64.pkg"` and never invokes `install.sh`, so a fetch living there would silently never run for cask users. ## Task 15: The offline proof, the certified constant, and the flag

**Files:**

- Modify: the certified-revision constant in `crates/gascan-arca/`

**The proof's shape already exists and is hardened.** `packaging/macos/release-smoke.sh:1015-1037` asserts six ways an offline sandbox has no egress — a test-owned host endpoint, a public IP, and public DNS, **each as the sandbox user and again as guest root** — and fails the release if any succeeds.
